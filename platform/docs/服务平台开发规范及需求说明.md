# 综合业务应用服务平台 — 功能需求文档

## 一、项目概述

本平台是面向多家企业的多租户应用服务平台。企业自行注册后，可为企业开通不同业务应用的试用或正式使用。平台采用应用优先（Plugin-First）的产品驱动增长模式，每个插件不仅是内部功能模块，也是可独立对外推广的产品。

平台负责应用市场、订阅生命周期、人工付款确认、功能授权、路由分发和数据空间分配；每个业务应用负责其内部业务用户的创建、登录、业务功能以及租户空间用量统计。

平台先支持中文，文案采用稳定的国际化 key 管理，为后续增加英文、日文等语言预留字典。

**技术栈约束**：项目开发采用 `python3.13` + `fastapi` + `vue3` + `sqlite3` 技术，为以后业务上升再升级调整预留空间。

### 核心数据边界

* 订阅、授权和数据空间以 **企业-应用（tenant-app）** 组合作为隔离主键。同一企业的不同应用之间数据完全隔离；不同企业使用同一应用时数据也完全隔离。


* 企业在平台的账号用于注册、应用市场和订阅管理。应用内业务用户由具体应用负责，与平台企业账号不是同一身份体系。


* **平台数据库与业务应用数据库严格分离**。平台数据库只保存企业、应用目录、版本、订阅、授权、配额、路由和审计等平台元数据，不保存或直接操作业务应用的业务表。


* 每个业务应用自行管理自己的数据库、文件和其他业务数据，并以企业租户及插件版本为隔离边界。**数据库命名严格遵循 `db_{plugin_id}_{tenant_id}_{version}` 规范**。


* 平台通过签发带有授权上下文的凭证（如 Token 或 Ticket），以**新开网页**的形式引导用户访问应用，**不需要在平台进行向底层应用进程注入不同的上下文 Header**；应用负责解析该凭证并动态切换对应租户的数据库连接。
* 平台日志和平台备份不计入企业空间使用量统计；应用自身的业务数据库、文件和其他业务数据计入该企业-应用空间。

## 二、角色定义

| 角色 | 描述 |
| --- | --- |
| **平台管理员** | 管理平台配置、企业、应用市场、数据留存、订阅申请和正式功能授权；人工确认线下付款。负责人工控制应用版本的起停、切换应用开放/维护状态、执行沙箱试运行与正式版本割接。

 |
| **企业平台账号** | 企业自行注册的平台账号，可浏览应用、开通试用、提交正式功能申请并管理本企业订阅。

 |
| **应用业务用户** | 在具体业务应用内由企业创建和管理，登录及业务权限由该应用负责。

 |
| **应用插件开发者** | 提供应用插件定义及授权接口实现；插件元数据同步本身不代表业务应用已完成接入。

 |

## 三、功能模块

### 3.1 企业注册与管理

企业可通过平台主入口注册，也可通过各个**应用插件的专属宣传页**直接无缝注册。注册成功后立即可以为已发布应用开通试用。平台管理员可查询、维护或停用企业，不代替企业创建应用内业务用户。

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| T-01 | **企业自行注册** | 创建企业平台账号和企业资料；同一企业身份需防止重复注册。**支持应用级无缝注册**（静默分配租户ID并立即生成试用快照）。

 |
| T-02 | **企业列表查询** | 管理员按企业、状态查询，查看企业已开通应用、功能授权和数据空间用量。

 |
| T-03 | **企业详情维护** | 查看和维护企业资料、启停企业平台账号；停用不直接删除其订阅和业务数据。

 |
| T-04 | **查看企业应用** | 查看每个企业-应用组合的试用/正式状态、功能申请与授权、有效期、配额及用量。

 |
| T-05 | **企业注销并销毁数据** | 企业可在平台主动注销，并销毁其试用期或正式使用期间产生的全部企业-应用业务数据；销毁后不可恢复。操作需二次确认并记录审计结果。不得保留已销毁的业务数据。

 |

### 3.2 应用市场与应用配置

平台管理员维护应用目录。每个应用配置自己的试用期、提醒时间、数据空间配额和功能模块。

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| A-01 | **接入业务应用** | 配置应用名称、编码、描述、图标、入口地址、版本、功能清单及授权接口信息。

 |
| A-02 | **应用市场展示** | 支持应用级独立推广，每个应用拥有专属宣传页（如 `/app/inventory/`）。企业可浏览已发布应用；管理员可查看全部应用并发布或下架。

 |
| A-03 | **应用级规则配置** | 平台管理员为每个应用配置试用期 `n` 个月、试用结束提醒提前 `m` 天、正式到期提醒提前 `m` 天及企业-应用空间配额。此类配置保存在平台，不要求插件 JSON 提供。

 |
| A-04 | **功能模块维护** | 配置功能编码、名称、描述、基础包/高级功能、展示价格和启停状态。

 |
| A-05 | **价格展示** | 价格只供企业了解和线下商议，不触发平台自动扣费或决定授权；实际付款由线下完成并由管理员确认。

 |
| A-06 | **下架与删除** | 下架后不可新开通试用；历史订阅、授权及审计记录保留。对已有数据的应用不做级联物理删除。

 |
| A-07 | **应用状态控制** | 平台可以设置该应用插件的全局**【开放】/【维护】**状态。维护状态下，已授权企业访问该应用时显示“系统升级维护中，暂停使用”，暂时禁止业务操作。 |
| A-08 | **版本起停控制** | 每个应用插件的不同版本均可通过平台人工控制【起停】。启动状态的版本可供访问，停止状态的版本释放资源。 |

### 3.3 登录、路由与新网页鉴权访问

系统采用按路径区分业务插件，并通过**新开网页传递鉴权凭证**的方式访问，URL 结构严格分为三层：

| 页面定性 | URL 结构示例 | 功能与路由规则 |
| --- | --- | --- |
| **公共宣传区** | `/app/{plugin_code}/` | **无状态展示**：展示插件功能、价格。直接放行至对应静态/宣传服务。 |
| **专属认证区** | `/app/{plugin_code}/login` | **统一认证入口**：展示带该应用专属 Logo 的登录/注册页。 |
| **私有业务区** | `/app/{plugin_code}/{tenant_code}/` | **专属工作区**：用户登录或平台跳转时，**新开网页**访问此地址。平台通过 URL 参数或验证 Token 传递身份契约，底层插件直接解析，**无需平台网关注入 Header**。 |

### 3.4 企业-应用订阅与功能授权

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| S-01 | **开通试用** | 企业从应用市场选择应用即可开通，无需付款；试用期为该应用配置的 `n` 个月，期间开放全部功能。

 |
| S-02 | **单次试用** | 每个企业-应用组合只能试用一次。重新注册、再次申请或导入数据均不能重置或延长试用期限。

 |
| S-03 | **申请正式使用** | 企业选择正式使用所需功能模块并提交申请。基础包必选。申请本身不授予所选功能权限。

 |
| S-04 | **人工确认与授权** | 平台管理员确认线下付款后，记录确认人和确认时间，正式授权从管理员确认时开始。仅开通管理员确认的功能，并向对应应用传递授权。

 |
| S-05 | **订阅查询** | 企业和管理员按应用/状态查看试用期限、正式期限、申请功能、已授权功能、提醒和空间使用情况。

 |
| S-06 | **正式期新增功能** | 正式使用期间可申请增加功能；管理员确认线下付款后立即开通。新增功能与原正式期共用到期日，费用按剩余天数折算。

 |
| S-07 | **正式续用** | 每次正式使用期限为一年。到期前确认续用，下一年度从当前到期日后开始；到期后确认续用，则从管理员确认日开始重新计算一年。

 |

### 3.5 状态与权限流转

```text
企业开通应用 → trial（试用中，全功能开放）
                    ├─ 申请正式功能 → pending_confirmation（等待人工确认，所申请功能尚未开通）
                    │                       └─ 管理员确认付款 → active（只开放确认功能）
                    └─ 试用到期 → trial_expired（停止应用访问，进入数据导出期）

active（正式使用中） → 到期 → expired（停止应用访问，进入数据导出期）
    ├─ 到期前确认续用 → 下一年度自原到期日后开始
    ├─ 到期后确认续用 → 新年度自确认日开始
    └─ 申请增加功能 → 管理员确认付款后立即开通，仍沿用原到期日

```

* `trial` 期间开放应用全部功能；`pending_confirmation` 不改变当前试用权限，也不提前开放所申请的正式功能。


* `active` 的功能权限以平台已确认的授权记录为准，应用不得仅凭前端状态开放功能。


* `trial_expired` 与 `expired` 均停止业务应用访问，但允许在导出期限内从管理平台导出数据。



### 3.6 数据空间、容量与导入

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| D-01 | **应用级空间配额** | 平台为应用配置适合其数据特征的配额，并将配额分配给每个企业-应用数据空间；业务应用负责统计自己管理的该空间实际用量并向平台提供用量信息。

 |
| D-02 | **用量提醒** | 用量达到配额 80% 时提示企业及管理员。

 |
| D-03 | **超限行为** | 应用度量确认用量超过 100% 后，禁止插入、提交和修改；允许查询、导出和删除。

 |
| D-04 | **试用反滥用识别** | 导入数据后可与其他企业相应应用数据进行相似度识别；高于 70% 时标记为可疑，由平台管理员复核。

 |

### 3.7 数据导出、封存与删除

* 试用到期或正式使用到期后，立即停止业务应用访问；从到期时点起，企业可在 30 天内通过平台管理平台下载对应企业-应用的数据。


* 30 天导出期结束后，数据封存 60 天；封存数据不可正常访问。封存期限结束后彻底删除企业-应用数据及其备份副本。

## 四、业务流程

### 4.1 无缝试用及正式开通流转 (Onboarding)

```text
访客访问某应用独立宣传页 (如 /app/inventory/)
   ↓
点击【免费试用】，跳转至该应用专属注册页 (/app/inventory/login 或 register)
   ↓
提交注册信息，平台后端静默创建新租户 (分配如 t002)
   ↓
平台静默分配试用期，生成数据快照/库
   ↓
平台生成授权凭证，新开网页跳转至专属私有业务区 (/app/inventory/t002/)
   ↓
... 试用到期前提醒 → 申请正式功能 → 线下付款 → 管理员授权生效

```

### 4.2 到期数据处理

```text
试用或正式授权到期 → 停止业务应用访问，开放 30 天平台数据导出[cite: 7]
   ↓
导出期结束 → 封存 60 天（可配置）[cite: 7]
   ↓
封存期结束 → 彻底删除数据及备份副本[cite: 7]

```

## 五、非功能需求

| 项目 | 要求 |
| --- | --- |
| **数据隔离** | 平台元数据与业务应用数据严格分离；企业-应用为业务数据强制隔离边界，不同企业、同企业不同应用的数据不能互相读取或操作。

 |
| **架构解耦** | 不强制要求平台向应用进程注入 Header，改为平台签发鉴权 Token 并通过新开网页的路由参数传递上下文，插件独立解析。 |
| **容量统计** | 应用负责实际用量统计；平台负责配额分配和展示。支持自适应全量度量、80% 提醒、导入分批度量与超限写保护。

 |
| **数据生命周期** | 到期 30 天导出、之后封存 60 天、期满彻底删除；时长可配置且任务可审计。

 |

## 七、应用插件升级与多租户底层隔离架构

为保障多租户系统下核心业务应用升级的“零风险”与高可用，平台采用沙箱化升级架构。

### 7.1 物理架构与版本起停设计

1. **进程隔离与人工起停**：每个应用插件的不同版本（如 `v2.2.0`）拥有独立的物理目录，平台在内存中启动对应版本的服务进程。**每个应用插件的不同版本都可通过平台人工控制起停**，启用的版本才可响应新开网页的访问。


2. **应用全局状态控制**：平台可以设置该应用插件的【开放】/【维护】状态。维护状态下阻断正常的业务进入。
3. **租户数据物理隔离**：单一进程并发处理多租户请求。所有业务数据按版本与租户独立分库，彻底规避越权风险（示例：`db_inventory_t001_v2.2.0`）。



### 7.2 智能结构判定与数据流转

插件包 `plugin.json` 需声明 `softwareVersion` (软件版本) 与 `dataVersion` (结构版本)。

* **结构未变**：新旧 `dataVersion` 相同，平台底层对数据库直接执行全量**复制**。


* **结构升级**：新旧 `dataVersion` 不同，平台调用插件包自带的迁移脚本（如 `upgrade.sh`），平台自动化注入新旧存储路径及新旧 DB URI。



### 7.3 三大鉴权契约模式与新开网页访问

平台不使用网关注入 Header，而是通过生成带有身份契约的 Token，**新开网页跳转**引导访问，插件内部解析契约。共支持 3 个鉴权契约模式：

1. **常规业务模式 (Normal)**
* **触发**：真实企业用户登录或访问。
* **契约传递**：签发携带 `{真实租户ID}` 的常规 Token，新开网页进入。
* **插件行为**：连接真实库，常规鉴权，**真实执行**短信/邮件等外部副作用。


2. **试运行上帝模式 (Sandbox God Mode)**
* **触发**：管理员在后台选择进入【虚拟沙箱租户】工作台。
* **契约传递**：平台签发包含 `tenant_trial` 及 `SANDBOX` 模式的强鉴权票据，新开网页进入。
* **插件行为**：解析票据免密放行，赋予 `SUPER_ADMIN` 最高权限，连接独立的沙箱库，**强制 Mock 拦截**所有对外发信/副作用操作。


3. **生产运维穿透模式 (Production Support)**
* **触发**：管理员为排障手动选定【真实企业租户】进入工作台。
* **契约传递**：平台签发包含 `{真实租户ID}`、`PRODUCTION_SUPPORT` 模式及 `{操作人ID}` 的特权票据，新开网页进入。
* **插件行为**：赋予该租户的超级权限，连接真实库并执行真实副作用；要求前端强制渲染红色危险警告边框，后端记录严格的越权审计日志。



### 7.4 上线割接与全量数据迁移流转 (SOP)

为保障数据绝对一致性，应用的升级发布严格遵循以下三阶段流转：

* **阶段 A：沙箱试运行准备 (UI状态：🧪 试运行)**
上传新版本后，平台不迁移全量租户数据，仅抽取指定租户（或虚拟沙箱数据）进行结构迁移。人工启动进程后，供管理员在新开网页的沙箱中验证，此时真实用户业务不受任何影响。


* **阶段 B：暂停服务与全量重迁 (UI状态：⏸ 切换中)**
试运行通过后触发【正式切换】。平台将插件应用状态设置为 **【维护】**（前端展示暂停横幅）。平台获取所有活跃租户列表，并发遍历执行基于旧版本最新数据的**重新全量复制/迁移**。


* **阶段 C：恢复与秒级回滚**
全量重迁完毕，将应用状态恢复为 **【开放】**。如遇重大故障，平台仅需修改主路由指向旧版本，实现利用原独立数据快照的秒级降级。
